# OneShot: план спасения за один день

Дата проверки: 12 сентября 2026. База: `db757b4fb71961a6acc20972bd454b8af1dc6e0c`.
Этот PR содержит план и исправления читаемости интерфейса. Работа по записи
нового live demo, интеграциям и продуктовой проверке ниже ещё не выполнена.
Исторический R0–R5 roadmap сохраняется в [plan.md](../plan.md).

## Граница плана

Рабочая сеть и платёжный rail здесь — только Arc Testnet (`eip155:5042002`)
с USDC. Production path получает сервис и quote из настроенной среды; synthetic
fixtures остаются тестовой опорой и не выдаются за платёжное доказательство.
Live-платёж и изменение внешней политики в этот план не входят.

## Решение

**OneShot помогает бизнес-агенту получить уже оплаченный API-результат после сбоя,
не создавая второй платёж.** Покупатель — разработчик бизнес-агентов. Сценарий —
одна покупка у одного подключённого поставщика через Privy и Arc Testnet.

За сутки не нужен поворот в treasury, DeFi-протокол или маркетплейс. Нужен
законченный путь: цена, разрешение, платёж, потерянный ответ, восстановление,
результат. Отличие от обычного payment SDK — долговечная идентичность задачи и
сохранение результата между перезапусками. Это гипотеза ценности, а не доказанный
спрос. Гарантия ограничена одним Business Intent и поддержкой поставщика;
произвольные внешние операции не становятся exactly-once.

## Требования спонсоров и приоритет

Проверены официальные страницы ETHOnline 2026; регистрацию команды из репозитория
подтвердить нельзя. В первые 30 минут владелец сверяет выбранный pool и разрешённый
объём ранее написанного кода. Не следует угадывать Continuity по возрасту репозитория.

1. **Privy — основной: Best B2B financial product.** Нужны Privy wallet,
   рабочая бизнес-операция, хотя бы один настоящий control, исходники и demo.
   Показываем разрешённую покупку и запрет неподходящей покупки. Login недостаточен.
   Best financial flow — дополнительная подача того же готового сценария.
   [Официальные требования](https://ethglobal.com/events/ethonline2026/prizes/privy).
2. **Arc — основной технический результат.** На проверенной странице нет Best Dev
   Tools. Для соответствующего pool доступны Best DeFi/Onchain Finance Application,
   Best Agentic Economy Application with Circle Agent Stack и Continuity Best DeFi
   or Agentic Application. Нужны работающие frontend/backend, схема архитектуры,
   видео/презентация, документация и исходники. Для первых двух наград $2,500 из
   $3,500 обусловлены mainnet до 30 сентября; Continuity — $2,000 из $3,000.
   Не обещаем эту часть награды и не включаем mainnet в сутки. Не заявляем Agent
   Stack без реального использования. [Требования Arc](https://ethglobal.com/events/ethonline2026/prizes/arc).
3. **The Graph — ограниченный дополнительный эпизод, AI Use Case.** Нужны live
   Graph provider, содержательное решение агента, публичный код и видео 2–4 минуты;
   выбираем pool по регистрации. Studio GraphQL подходит. Один Subgraph допустим
   для AI, но не доказывает Composable/Standardized. Не строим второй Subgraph или
   MCP только ради списка технологий. [Требования Graph](https://ethglobal.com/events/ethonline2026/prizes/the-graph).

## План на 24 часа и критерии остановки

Часы считаются от начала исполнения плана. Один ответственный за каждый блок;
это последовательный бюджет небольшой команды, не обещание работы трёх инженеров.

| Время | Ответственный | Действие | Проверяемый результат |
| --- | --- | --- | --- |
| 0–1 | Владелец + разработчик | Подтвердить pool; выбрать один тестовый supplier; зафиксировать SHA/revisions, сеть, миграцию и текущие сбои | Одна карточка demo, понятный scope и доступная среда |
| 1–4 | Frontend | Применить UI-исправления этого PR, проверить кабинет и обе темы | Читаемость, контраст обычного текста >=4.5:1, одинаковые края header/login/results на 390 и 1440 px |
| 4–7 | Backend/operator | Провести покупку через существующий UI/API и durable worker; сохранить ключ и результат | Один intent, один платёж, исходный результат после повторного запроса |
| 7–10 | Backend/operator | Проверить разрешение и отказ Privy; правила подписания и typed data; изолированный failure drill | Запрет даёт ноль внешних платежей; UNKNOWN не разрешает повторную оплату |
| 10–12 | Разработчик | Повторить clean checkout quickstart; проверить маленький пример клиента с тем же task key | Другой разработчик получает результат без правок исходников и нового framework |
| 12–14 | Recovery/operator | Дать Graph не более 2 часов: живое обнаружение, Arc verification, advisor trace | Полная трасса либо честное NOT VERIFIED; затем заморозка функциональности |
| 14–16 | Владелец + 2–3 внешних разработчика | Короткая проверка концепции и понятности UI | Записаны действия, время, ошибки и решение о позиционировании |
| 16–20 | Разработчик/reviewer | Локальные проверки, FreePi Gate A, draft PR, required CI, Gate B | Точный tree/head проверен; при сбое остаётся draft |
| 20–22 | Владелец | Записать 2–4-минутное видео и короткую презентацию | Видны результат, один платёж, правила и пределы гарантии |
| 22–24 | Владелец | Повторить demo, проверить публичные ссылки; резерв на исправления | Готовая заявка для ручной отправки, без неподтверждённых claims |

Если к часу 7 x402 не даёт результат: использовать уже существующий team-operated
report/direct Arc сценарий и честно назвать поставщика командным. Не менять rail
для уже UNKNOWN intent и не создавать ему замену. Если отказ Privy не доказан,
B2B qualification остаётся NOT VERIFIED. Если Graph не доказан за 2 часа, основной
платёжный demo продолжается без Graph qualification. Любой риск второго платежа
останавливает платёжный сценарий независимо от дедлайна.

## Demo: четыре минуты, один понятный результат

1. **0:00–0:25 — проблема.** «Наш агент купил API-результат. Соединение пропало.
   Как продолжить работу и не заплатить дважды?» Показать один выбранный сервис.
2. **0:25–1:00 — разрешение.** Privy login, execution wallet и реальное разрешение
   показать отдельно. Проверить цену/получателя/Arc Testnet, сохранить task key,
   подтвердить покупку. Предварительно фондированный Gateway обозначить явно.
3. **1:00–2:00 — сбой и возврат.** Через проверенный default-off hook потерять
   ответ после broadcast; показать UNKNOWN. Второй клиент использует тот же ключ;
   recovery читает прежние доказательства, не отправляет платёж заново.
4. **2:00–2:40 — полезный результат.** Показать сохранённый ответ поставщика,
   тот же intent и проверенную Arc транзакцию. Счётчики считать по durable ledger
   и внешним доказательствам, а не по числу нажатий или строк в UI.
5. **2:40–3:15 — ограничения.** Отдельный запрещённый запрос получает отказ Privy
   и ноль платежей. Коротко объяснить: ограничение кошелька плюс защита OneShot.
6. **3:15–3:45 — Graph, только если доказан.** Отдельный явно обозначенный
   direct-transfer hashless drill: live Studio candidates, _meta, решение модели,
   Arc verification, core disposition. Gateway x402 может не дать ERC-20 кандидата;
   отсутствие Graph-кандидата не означает отсутствие платежа.
7. **3:45–4:00 — итог пользователя.** Результат получен, существующая оплата
   сохранена. Указать testnet, team-operated supplier и ограничения гарантии.

При медленной индексации использовать запись успешного реального прогона с датой
и SHA, пометить монтаж/ускорение. Offline fixture допустима для объяснения сбоя,
но не заменяет live proof. Не удалять durable evidence и не скрывать работающий
provider lookup ради эффектного Graph-сюжета. Подробности и безопасный hook:
[DEMO_SCRIPT.md](DEMO_SCRIPT.md), [CIRCLE_X402_DEMO.md](CIRCLE_X402_DEMO.md).

## Как усилить Arc с точки зрения разработчика

Самый полезный вклад — воспроизводимый рецепт безопасного возобновления покупки
на Arc, собранный из существующего кода. За день не нужен новый SDK/контракт.

- Quickstart должен вести от clone до одной покупки и повторного чтения того же
  результата. Переиспользовать API clients и `demo:r4`; CLI `demo:x402` сам по себе
  имеет in-process guard и не доказывает безопасность после рестарта.
- Разделить идентичности: task key, Business Intent, Circle transfer UUID и Arc tx
  hash. UUID нельзя отправлять в explorer как hash. Показать один реальный пример
  с очищенными доказательствами и без секретов.
- Явно разделить обычный ERC-20 receipt и Gateway `submitBatch`/`BatchProcessed`.
  Это уже реализовано; задача — сделать поведение понятным и воспроизводимым.
- В документации объяснить 6 знаков ERC-20 USDC и 18 знаков native balance/gas;
  суммы API остаются строками integer atomic units. Проверка сети — 5042002.
  [Arc integration](https://docs.arc.io/integrate/infrastructure),
  [stablecoin model](https://docs.arc.io/arc/concepts/stablecoin-native-model).
- Использовать read-only Circle transfer lookup при наличии UUID;
  [официальный API](https://developers.circle.com/api-reference/gateway/all/get-x402transfer-by-id).
  Отсутствие окончательной транзакции означает ожидание, а не новую оплату.

Критерий DX: сторонний разработчик за 15 минут на подготовленной testnet среде
проходит README без подсказок, повторяет тот же task key и находит исходный
результат/receipt. Если не проходит — исправить один мешающий шаг, не писать SDK.

## Как улучшить использование правил

**Правила кошелька.** Заменить статическое Protected на подтверждённое состояние
или «Not verified», показывать источник, сеть, допустимый recipient, фактический
лимит и время проверки. Использовать существующий config/read endpoint, если он
содержит безопасные данные; иначе в эти сутки честно назвать экран описанием
контролей, не добавляя редактор политик. Ключи и runtime secrets не возвращать.
Проверить все методы нормального signing path: правила Privy привязаны к RPC
методу, поэтому контроль sendTransaction сам по себе не доказывает контроль
signTransaction или signTypedData. [Privy policy semantics](https://docs.privy.io/controls/policies/overview).

**Правила разработки.** Сохранить одну каноническую `.agent/` policy. Для каждого
изменения записывать acceptance, выбранные Test Matrix cases и результат в одном
context record. В `plan.md` отделять план от кода и live evidence. Gate A/B
привязывать к immutable tree/SHA; не переносить старые verdict на новый код.
Проверки цветов дополнить браузерным контрастом: токены по отдельности проходят
тест, но их неправильная комбинация на реальной карточке была нечитабельной.
Этот PR не отменяет review gates и не создаёт новую систему правил.

## Проверка концепции и безопасности

Дать 2–3 разработчикам одинаковое задание: «Купить тестовый результат, закрыть
страницу, восстановить задачу, объяснить, будет ли новая оплата». Не подсказывать.
Записать время до результата, ошибки с task key и смог ли человек отличить Paid
от Result available. Спросить о последнем реальном случае повторной оплаты или
потери результата. Успех на день: минимум 2 человека завершают сценарий и верно
объясняют гарантию. Это usability signal, не подтверждение рынка.

Обязательные технические проверки до submission:

- Normal purchase, identical request twice, 10 последовательных повторов,
  10 параллельных workers и два клиента: одна исходная идентичность и не более
  одного внешнего settlement; изменённый payload с тем же ключом конфликтует.
- До submit: безопасный отказ и ноль платежей. После возможного submit/рестарта:
  UNKNOWN, reconciliation и ноль новых submission. После commit и сбоя supplier:
  исходный платёж остаётся, повторяется только допустимое получение результата.
- Privy deny/over-limit: ноль settlement. Graph empty/stale/multiple/injected
  и invalid model output: UNKNOWN/hold, модель не получает signing capability.
- Использовать существующие `pnpm test`, `pnpm test:integration`,
  `pnpm scenarios:invariants`, `pnpm demo:r4` и [Test Matrix](../.agent/TEST_MATRIX.md).
  Offline и live результаты записывать раздельно; интеграционный тест без
  PostgreSQL/container runtime не считать пройденным.
- Для UI: обе темы, все вкладки выбранные и невыбранные, quote, input, result,
  hover/focus, 390/1440 px. Проверять фактический контраст, ширину и overflow.

Не добавлять за день: marketplace, второй supplier, multi-chain, pooled budgets,
автономные изменения Privy policies, новую модель, MCP server или mainnet.
Единственная допустимая новая пользовательская функция после устранения сбоев —
удобное возвращение к существующему результату, если текущего Requests недостаточно.

## Готовность к записи и отправке

Перед записью: один точный Git SHA и deployed revisions, применённая миграция,
доступный testnet balance, работающий quote, стабильный ключ, полученный результат,
Arc receipt и очищенная denial/recovery трасса. Отдельно подтверждены pool и
публичность исходников. Перед отправкой: локальные проверки, Gate A, required CI,
Gate B, видео, схема и корректные sponsor statuses. Владелец вручную отправляет
заявку и выполняет merge; этот план не является разрешением на mainnet.
